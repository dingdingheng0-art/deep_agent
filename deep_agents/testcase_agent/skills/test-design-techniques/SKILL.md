# 测试用例设计方法库

基于 `/analysis/test_points.md` 设计完整、可执行测试用例的方法论。

## 方法选择决策表

按测试点特征选择主设计方法（一条用例填一个主方法，可组合使用）：

| 测试点特征 | 首选方法 | 辅助方法 |
|---|---|---|
| 输入域有合法/非法类别划分 | 等价类划分 | 边界值分析 |
| 输入有数值/长度/日期范围 | 边界值分析 | 等价类划分 |
| 跨页面的业务流程（基本流+备选流） | 场景法 | 状态迁移 |
| 多条件组合决定不同动作 | 判定表 | 等价类划分 |
| 对象有明确状态机（订单、审批流） | 状态迁移 | 错误推测 |
| 无明确规则、依赖经验 | 错误推测 | — |

## 六大方法操作要点

### 1. 等价类划分
- 把输入域划分为若干有效等价类 + 无效等价类，每类取一个代表值。
- 一条用例尽量**覆盖多个有效等价类**（减少用例数）；无效等价类**一条用例只覆盖一个**（避免错误掩盖）。

### 2. 边界值分析
- 对每个范围 [min, max] 取：min-1、min、min+1、max-1、max、max+1（开区间相应调整）。
- 长度类边界同理：0、1、最大、最大+1。
- 边界值必须写**具体数字**进测试数据，禁止写"超长""过大"。

### 3. 场景法
- 从需求流程中梳理基本流（happy path）与备选流（异常分支、可选分支）。
- 每个"基本流 + 备选流组合"构成一个场景 → 一条用例；步骤要覆盖场景涉及的每个页面动作。

### 4. 判定表
- 列出所有条件桩（输入条件）与动作桩（系统行为），枚举规则列。
- 条件数 n → 规则数 2ⁿ，超过 4 个条件时用合并/正交思路裁剪，并在用例中注明取舍。
- 每条规则至少一条用例，测试数据写明各条件取值。

### 5. 状态迁移
- 画出状态节点与迁移边，覆盖：每条合法迁移一条用例；每条**非法迁移**一条用例（验证被拒绝）。
- 前置条件写清对象的初始状态。

### 6. 错误推测
- 基于经验补充：空/null、重复提交、并发、刷新/回退、网络中断恢复、缓存脏数据、时区与夏令时、数字精度（0.1+0.2）、极大数溢出。
- 用于补漏，不替代上面的系统性方法。

## 优先级判定规则

| 优先级 | 判定标准 |
|---|---|
| P0 | 核心业务流程主路径；涉及资金、数据安全、不可逆操作；阻断性缺陷高发区 |
| P1 | 主要功能的备选流；常见异常处理；重要边界值；权限校验 |
| P2 | 低频场景；界面展示；兼容性；提示文案 |

分布参考：P0 约 20–30%，P1 约 40–50%，P2 约 20–30%。P0 超过 50% 说明优先级判断过松。

## 用例写作规范（强制执行）

1. **步骤原子化**：一步一个操作，写明操作对象与值（"在【手机号】输入框输入 13800001111"），禁止"输入正确信息"这类笼统描述。
2. **预期可判定**：写具体可观察结果（"页面跳转至首页，顶部显示昵称'张三'"），禁止"操作正常""提示正确"。步骤有多个预期时分点对应。
3. **测试数据具体化**：给出真实可用的取值（账号、手机号、金额），不写"任意""合法数据"。
4. **前置条件完整**：包括登录态、角色、已有数据、对象初始状态。
5. **用例独立**：用例间不得依赖执行顺序。
6. **编号规则**：`TC_` + 三位序号（TC_001…），全表唯一、连续。

## 覆盖均衡要求

- `/analysis/test_points.md` 中**每个测试点至少一条用例**，设计时在脑中维护映射，写完后抽查 3 个功能点验证无遗漏。
- 正常 : 边界/异常 用例数大致 1 : 1——只测正常流是新手最常见的缺陷。
- 修订模式下：评审意见的每条"必须修改"都要落实到具体用例（改/删/增），并在总结中说明逐条处置结果。
