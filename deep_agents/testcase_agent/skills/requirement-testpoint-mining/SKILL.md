# 需求测试点挖掘

把需求文档转化为「模块 → 功能点 → 测试点」三层结构化清单的方法论。

## 核心原则

1. **测试点 ≠ 需求复述**：测试点是"需要验证的角度"，一条需求通常派生多个测试点。
2. **维度驱动挖掘**：对每个功能点，逐个过一遍下方的「测试维度清单」，命中即生成测试点，避免凭直觉遗漏。
3. **可追溯到需求**：每个功能点保留需求描述与业务规则原文要点，供后续设计、评审核对。

## 挖掘流程（四步）

### 第 1 步：通读与切块

- 通读 `/uploads/` 下全部解析产物，识别文档结构（章节、功能列表、流程图、表格）。
- 按业务模块切块；文档较长时用 `grep` 定位关键词：输入、限制、必须、不可、最多、至少、当…时、如果、否则、权限、角色、状态。

### 第 2 步：提取功能点

对每个模块提取功能点，每个功能点记录三要素：

- **需求描述**：系统要做什么（一句话）；
- **业务规则**：约束条件原文要点——输入范围、格式校验、计算公式、状态流转、权限要求；
- **输入/输出**：关键字段及其类型、取值范围。

规则藏在表格和流程图里时，必须展开为文字（docling 已将图表描述化，注意阅读图片说明）。

### 第 3 步：按维度展开测试点

对**每个功能点**逐项过下面的维度清单，命中的维度至少生成 1 个测试点：

| 维度 | 关注点 | 典型测试点示例 |
|---|---|---|
| 正常流程 | 主路径、最常见输入 | 合法输入完成业务闭环 |
| 备选流程 | 需求中的"或/也可以/支持多种" | 每种备选路径各一条 |
| 边界值 | 数字长度/大小/日期的最小、最大、临界±1 | 0 与 1、最大长度与最大+1、起止日期当天 |
| 异常输入 | 空、非法格式、类型错误、超长、特殊字符、SQL/脚本注入串 | 必填项留空、负数、emoji、`<script>` |
| 权限 | 不同角色、未登录、越权访问 | 无权限角色触发操作、横向越权改他人数据 |
| 状态流转 | 状态机每个合法/非法迁移 | 已取消订单再支付、重复提交 |
| 并发与重复 | 重复点击、重复提交、并发操作同一数据 | 双击提交只生成一条记录 |
| 数据一致性 | 增删改后关联数据、列表与详情、统计口径 | 删除后列表/统计同步更新 |
| 兼容性 | 浏览器/分辨率/移动端（如需求提及） | 需求声明的环境矩阵抽查 |
| 易用性 | 提示文案、错误提示、加载态（仅当需求有约定） | 错误提示语与需求一致 |
| 性能 | 仅当需求写明指标（响应时间、数据量） | 大数据量下分页/查询 |
| 安全 | 仅当需求涉及敏感数据 | 敏感信息脱敏展示 |

> 不是每个功能点都要覆盖全部 12 个维度——只挑与需求相关的；但"正常/边界/异常"三类对输入型功能点**强制覆盖**。

### 第 4 步：自检与产出

对照「遗漏自检表」检查后再写文件。

**遗漏自检表**：

- [ ] 每个需求章节都映射到了至少一个功能点？
- [ ] 每个含输入的功能点都有边界值与异常输入测试点？
- [ ] 文档中的每个"如果/当…时/否则"分支都有对应测试点？
- [ ] 流程图/状态图的每条边都有测试点？
- [ ] 表格里的每条规则都展开了？
- [ ] 有权限/角色要求的功能点都有越权测试点？

## 输出模板

写入 `/analysis/test_points.md`：

```markdown
# 测试点清单

> 需求来源：<文档名> ｜ 模块 X 个 ｜ 功能点 Y 个 ｜ 测试点 Z 个

## 模块一：<模块名>

### 功能点 1.1：<功能点名>
- 需求描述：……
- 业务规则：……（逐条列出约束）
- 测试点：
  - [正常] ……
  - [边界] ……（标注具体边界值，如"密码长度 8（最小值）/ 21（最大+1）"）
  - [异常] ……
  - [权限] ……
```

测试点描述要**带具体值**（"密码长度 21 位（最大 20+1）"优于"密码超长"），为后续边界值设计直接供料。

## 收尾

清单写完后，用一两段话总结：模块数、功能点数、测试点数，以及哪些功能点因需求描述模糊做了假设（列出假设内容，供用户确认）。
