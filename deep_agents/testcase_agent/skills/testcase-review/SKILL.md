# 测试用例评审方法论

审查 `/testcases/testcases.md` 的质量与覆盖率，产出可执行的评审意见。

## 评审姿态

- **严格优先**：宁可多提问题，不放过遗漏。模糊即问题。
- **意见可落地**：每条问题必须标注用例编号 + 具体修改建议，禁止"建议加强覆盖率"这类空话。
- **对单不对人**：只陈述事实与依据（引用测试点清单或业务规则原文）。

## 评审流程

### 第 1 步：构建覆盖矩阵（覆盖率审查的核心动作）

逐行扫描 `/analysis/test_points.md` 的每个测试点，在 `/testcases/testcases.md` 中找对应用例，建表：

| 模块 | 功能点 | 测试点 | 对应用例编号 | 状态 |
|---|---|---|---|---|
| 登录 | 1.1 密码登录 | [边界] 密码长度 21 位 | TC_007 | ✅ 已覆盖 |
| 登录 | 1.1 密码登录 | [异常] SQL 注入串 | — | ❌ 遗漏 |

- 任何测试点找不到对应用例 → **必须修改**。
- 统计：测试点总数、覆盖率 = 已覆盖/总数。覆盖率 < 100% 结论必须为"需修改"。

### 第 2 步：五维审查

**① 覆盖率**（除矩阵外）
- 正常/边界/异常三类是否均衡？正常用例占比 > 70% 即为失衡。
- P0 级业务流的备选流是否都有用例？

**② 正确性**
- 预期结果是否与业务规则矛盾？（对照测试点清单中的"业务规则"逐条核对）
- 测试数据是否满足用例声称的场景？（如"测试超长密码"但数据只有 10 位）
- 设计方法使用是否得当？（多条件组合却没用判定表 → 建议优化）

**③ 可执行性**（逐条抽查，重点抽 P0）
- 步骤是否具体到操作对象与值？出现"输入正确信息""进行相关操作" → 必须修改。
- 预期结果是否可判定？出现"正常""正确""成功提示"而无具体内容 → 必须修改。
- 前置条件是否完整（登录态/角色/初始数据）？
- 用例间是否有隐藏的执行顺序依赖？

**④ 规范性**
- 编号是否唯一、连续、格式统一（TC_三位序号）？
- 十个字段是否齐全（缺失字段列出用例编号）？
- 优先级分布是否合理（P0 占比 20–30% 为正常，>50% 说明标级过松）？
- 用例类型/设计方法取值是否在约定集合内？

**⑤ 冗余度**
- 标题/步骤/预期高度相似的用例对：标注并建议合并或说明各自差异点。
- 同一边界值被多条用例重复验证而无新场景 → 建议优化。

### 第 3 步：问题分级

| 级别 | 判定标准 | 处置 |
|---|---|---|
| 必须修改 | 测试点遗漏；预期与规则矛盾；步骤/预期不可执行；编号重复；测试数据错误 | 逐条列出，修订必须全部落实 |
| 建议优化 | 方法选择欠佳；冗余用例；优先级分布失衡；表述可更清晰 | 可选采纳 |

**总体结论判定**：
- 存在任何"必须修改" → 结论 = **需修改**；
- 只有"建议优化" → 结论 = **通过（附优化建议）**。

## 输出模板

写入 `/review/review.md`：

```markdown
# 测试用例评审意见

## 总体结论
需修改（测试点覆盖率 87%，3 条用例预期结果不可判定）/ 通过（附 N 条优化建议）

## 覆盖率分析
| 模块 | 功能点 | 测试点 | 对应用例 | 状态 |
|---|---|---|---|---|
……（全量矩阵）
覆盖率：已覆盖 X / 总 Y = Z%

## 必须修改
1. **[TC_012]** 预期结果"登录失败提示正确"不可判定 → 改为具体提示文案"密码错误，还可尝试 4 次"。
2. **[遗漏]** 测试点 1.3 [异常] 验证码过期 → 新增用例：验证码生成 5 分 01 秒后提交。

## 建议优化
1. TC_020 与 TC_021 步骤预期高度相似，建议合并或注明差异场景。
2. P0 占比 45% 偏高，建议复核 TC_031/TC_035 是否确为核心流。

## 修订核对清单
- [ ] 必须修改 1
- [ ] 必须修改 2
……（供修订后逐条勾选核对）
```

## 收尾总结

回复中给出：总体结论、必须修改条数、建议优化条数、覆盖率数字。不要复述全部评审内容（已在文件中）。
